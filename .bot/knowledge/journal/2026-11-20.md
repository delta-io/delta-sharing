# Learning journal 2026-11-20

### 2026-11-20: CI bot security — Run agent-authored test code under an allowlisted environment, not just cloud-creds-stripped
**Context:** In PR #1048 a reviewer noted `bot-test.sh` unset cloud credentials but left `DATABRICKS_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN` in the environment, where a prompt-injected test (the task comes from an attacker-writable issue body) could exfiltrate them.
**Rule:** When a CI job executes test or build code that an agent generated from untrusted input, run it with an allowlisted environment (`env -i` plus only PATH/HOME/JAVA_HOME/cache vars), never relying on stripping a subset of secrets.

### 2026-11-20: CI bot security — Split a read-only agent token from a short-lived write token minted only for publishing
**Context:** In PR #1048 the engineer follow-up workflow granted contents/pull-requests/issues write for the whole run (including while running agent tests), unlike the author workflow which kept the agent read-only and minted write only to publish.
**Rule:** Keep the agent step on a read-only token and mint a fresh write token only for the publish/push step, so test execution never runs with write (tag/release-capable) scope.

### 2026-11-20: Scala client concurrency — Never sleep for retry/backoff while holding a monitor that close() also synchronizes on
**Context:** In PR #962 a reviewer found `RandomAccessHttpInputStream.read()` runs `runWithExponentialBackoff` (Thread.sleep up to 10 min) while holding the object monitor; a concurrent synchronized `close()` (e.g. Spark task cancellation) then blocks for the entire retry duration, and the retry lambda also nests another retry via `reopen`.
**Rule:** Do not perform blocking retry/backoff sleeps inside a synchronized method whose monitor cancellation/`close()` needs, and avoid nesting a retry loop inside another retry loop (multiplicative backoff).

### 2026-11-20: CDF correctness — Derive _change_type for removeFile/addFile from the action, never from the parquet file
**Context:** In PR #992 the `test_add_column_partitioned_cdf` case exposed that CDF-enabled tables can have a legitimately null `_change_type` column in raw (non-CDC) parquet files; reading it from the file yielded `None` instead of `delete`.
**Rule:** For CDF materialization, always derive `_change_type` for removeFile and addFile actions from the action type itself, not from any `_change_type` column present in the parquet data.

### 2026-11-20: Delta Sharing client — Treat response version as optional and gate versionless-CDF on the advertised capability
**Context:** PRs #1005/#1006/#1007 added CDF-on-views: `ParsedDeltaSharingResponse.version` became `Option[Long]` (null for versionless CDF), the client treats the versionless response as a snapshot query, and the server only responds when the client advertises `versionlesscdf` in its capabilities header.
**Rule:** Make the sharing-response `version` optional/nullable on the versionless-CDF path and only emit or expect versionless-CDF behavior when the client has advertised the `versionlesscdf` capability.
